GOAL

A manager can load the fictional scenario, edit the brief, start a session, answer or skip clarification questions, and receive a qualitative comparison and recommendation generated by OpenAI.

Keep the existing three-panel layout. This iteration makes it functional; visual refinement, revision interaction, exports and persistence come later.

1. OPENAI INTEGRATION

Use the official asynchronous Python SDK, Responses API and native Structured Outputs with Pydantic.

Consult the current official documentation:

* https://developers.openai.com/api/docs/guides/structured-outputs
* https://developers.openai.com/api/docs/libraries
* https://developers.openai.com/api/docs/models/gpt-5-mini

Keep the existing configuration names:

* MODEL_PROVIDER=openai
* MODEL_NAME=gpt-5-mini as the initial, configurable default
* MODEL_API_KEY supplied privately through the local environment or git-ignored `.env`

Do not silently switch models. Check compatibility between the generated schemas, the SDK and the selected model. Preserve application-level validators even where the API cannot enforce them.

Handle missing credentials, authentication errors, rate limits, timeouts, refusals and incomplete output explicitly. Never replace a failed live call with sample output.

The application must still start without a key. Explain how I can configure it locally without asking me to paste it into the conversation.

2. RUNTIME PROMPTS

Implement the prompt loader and the runtime files needed for:

* Advisor instructions.
* Next-action selection.
* Diagnosis.
* Requesting essential context.
* Clarification.
* Comparison.
* Recommendation.
* Repairing invalid output.

Use the existing action mapping. Advertise only actions actually supported by this iteration; revision remains unavailable.

Keep advisory instructions in files under `backend/prompts/`, with identifier, version, inputs, outputs and constraints. Load their current contents when executing them and record a content hash for traceability.

Prompts should request concise decision explanations, distinguish supplied information from assumptions, and avoid unsupported certainty about costs, feasibility, timing or returns.

Correct the worked examples accordingly. In particular, a €60,000 budget does not establish infeasibility without an estimate of the initiative's costs. Preserve their accurate attribution as manually authored fictional examples.

Treat manager-provided text as case information, not as instructions that can override the advisor or its controls.

3. ADVISORY EXECUTION AND STATE

Implement a small bounded advisory loop. The next-action prompt chooses what happens next; Python enforces permitted actions and their prerequisites.

Use temporary in-memory sessions for this iteration and document that they disappear on restart. Store the brief, clarification rounds and validated advisory outputs separately. The model must never invent or modify the manager's answers.

Pause when user input is requested or a recommendation is ready. Implement `await_user` without an unnecessary additional model call.

Enforce explicit limits on actions, model requests, input size and execution time. Include selector and repair calls in the request budget. Allow at most one repair attempt per invalid output, and avoid hidden retry multiplication.

Preserve unanswered and skipped questions in session state. Display them from that state even if a generated summary omits them.

4. VALIDATION BEFORE STATE CHANGES

Add one explicit validation boundary used by every executed action before accepting its output.

Check:

* The output contract.
* Context identity.
* Referenced initiatives and source identifiers.
* Question identity and answer status.
* Required prior outputs, such as a comparison supporting a recommendation.

Add regression coverage for the review findings: an unrelated context ID and a nonexistent revision constraint currently pass the existing checks.

For revision validation, require actual previous/current snapshots and check reported constraint changes against them. This does not require implementing the revision user flow yet.

Prevent overlapping requests from committing stale results to a session. Invalid output must not replace previously validated advice.

5. MINIMUM FUNCTIONAL INTERFACE

Wire the existing panels to the backend:

* Load and edit the fictional brief with labelled inputs.
* Start an advisory session.
* Display diagnosis and requests for information.
* Answer or explicitly skip clarification questions.
* Show qualitative comparison and the current recommendation.
* Show loading, recoverable errors and remaining unknowns.

For now, editing the initial brief after a session starts should clearly start a new session rather than pretend to revise existing advice.

Keep provider credentials and technical execution details out of the manager's main workflow. Developer metadata can remain in diagnostics.

Offline replay is still deferred. Test doubles must not appear as live model output in the application.
